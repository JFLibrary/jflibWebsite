cargo jflib test

Test che si leggono come istruzioni.

Uno script .uis usa la tua app come farebbe una persona. Clicca, digita, trascina, scorre con il dito e preme tasti, poi controlla cosa è successo. Fa girare l’app vera senza finestra, su un orologio virtuale, così ogni esecuzione finisce con lo stesso risultato e gli stessi pixel, sulla tua macchina e in CI.

Guarda uno script in azione Il linguaggio nella guida

Una riga, un passo.

Questo script compila una parte della galleria delle funzionalità. Ogni immagine mostra l’app subito dopo quella riga. Le righe che iniziano con expect sono le verifiche. Clicca una riga per saltarci.

  1. click #700
  2. type "Ada Lovelace"
  3. expect #700 text "Ada Lovelace"
  4. click "Option A"
  5. expect checkbox:"Option A" unchecked
  6. click "Blue"
  7. expect radio:"Blue" checked
  8. drag 105,446 186,446 12
  9. expect #140 value 84
  10. key tab up up
  11. expect #141 focused
  12. expect #141 value 14
  13. theme dark

Perché funziona così bene.

L’app vera

Niente mock e niente build di test. Lo script passa all’app compilata gli stessi eventi che le passerebbe la piattaforma.

Headless

L’app disegna in memoria. Non si apre nessuna finestra, nessuno ti ruba la tastiera, e lo esegue anche un server senza desktop.

Deterministico

Il tempo è un orologio virtuale a frame da 16 ms. Timer e animazioni lo seguono, così un’esecuzione non aspetta mai e non fallisce mai a caso.

Selettori leggibili

Indica un widget per etichetta, per tipo ed etichetta, per id o con un punto. Regole chiare decidono quando un’etichetta compare due volte.

Errori chiari

FAIL line 9: … indica la riga e cosa è stato trovato al suo posto. Lo script va avanti, e il codice di uscita lo comunica alla CI.

Un solo linguaggio ovunque

Gli stessi script girano su Windows e Linux, e pilotano anche l’inspector.

Tutto ciò che può fare una persona.

E qualcosa che una persona non può: uno script può rilasciare file da un altro programma, sospendere l’app, passarle letture di sensori o perdere la GPU, tutto senza un dispositivo vero.

Verifica ciò che conta, fino al pixel.

Le verifiche leggono stati, valori, testi e rettangoli dagli stessi dati che vedono i lettori di schermo e l’inspector. Quando contano i pixel, uno script confronta un punto, un’area o l’intera finestra con un’immagine precedente, byte per byte.

  • Stati: exists, focused, checked, disabled, selected, open, pressed e altri.
  • Valori, intervalli, testi e rettangoli in pixel indipendenti dal dispositivo.
  • Token del tema, lo stile in uso, i suoni richiesti e gli avvisi stampati.
  • --verify-dirty confronta ogni ridisegno parziale con uno completo, così un pixel mancato non può nascondersi.
expect button:"Send" disabled
type "Hi"
expect button:"Send" enabled
expect #140 value 40..60
expect text:"Saved" exists
expect #9 rect * * * 36
expect pixel 12 40 #0067C0
expect token accent_text #FFFFFF

shot before.png
theme dark
theme light
expect same before.png       # byte per byte

Budget dei frame come test.

bench misura frame veri mentre le cose si muovono: un’animazione, un trascinamento, una serie di scatti della rotellina. Stampa la media, la mediana e il frame peggiore, e con un limite fallisce quando la mediana supera il budget. Tre tentativi compensano una macchina di build sotto carico.

Il test di prestazioni di JFNetworker sposta, ingrandisce e trascina così una rete di 500 dispositivi e 800 cavi a 1920 × 1080.

# 300 frame di un trascinamento, al massimo 16,6 ms ciascuno
bench 300 drag #50 900,500 16600

# scorrimento fluido
wheel 500,400 -360
bench 60 anim 16600

Ogni nuova app parte con un test che passa.

cargo jflib new scrive tests/smoke.uis accanto al tuo codice. cargo jflib test compila l’app ed esegue ogni script in tests/. Una prima riga #!args passa argomenti al programma, e dump stampa l’albero dei widget con id e posizioni quando scrivi un nuovo script.

L’inspector mostra il selettore di qualsiasi widget che punti, pronto da incollare.
