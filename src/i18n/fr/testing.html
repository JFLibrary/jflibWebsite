cargo jflib test

Des tests qui se lisent comme des instructions.

Un script .uis utilise votre application comme le ferait une personne. Il clique, tape, glisse, balaie l’écran et appuie sur des touches, puis vérifie ce qui s’est passé. Il exécute la vraie application sans fenêtre, sur une horloge virtuelle : chaque exécution aboutit au même résultat et aux mêmes pixels, sur votre machine comme en CI.

Voir un script s’exécuter Le langage dans le guide

Une ligne, une étape.

Ce script remplit une partie de la galerie des fonctionnalités. Chaque image montre l’application juste après la ligne correspondante. Les lignes qui commencent par expect sont les vérifications. Cliquez sur une ligne pour y aller directement.

  1. click #700
  2. type "Ada Lovelace"
  3. expect #700 text "Ada Lovelace"
  4. click "Option A"
  5. expect checkbox:"Option A" unchecked
  6. click "Blue"
  7. expect radio:"Blue" checked
  8. drag 105,446 186,446 12
  9. expect #140 value 84
  10. key tab up up
  11. expect #141 focused
  12. expect #141 value 14
  13. theme dark

Pourquoi ça marche si bien.

La vraie application

Ni mocks ni build de test. Le script envoie à l’application compilée les mêmes événements que la plateforme.

Sans fenêtre

L’application dessine en mémoire. Aucune fenêtre ne s’ouvre, rien ne vous vole le clavier, et un serveur sans bureau peut aussi l’exécuter.

Déterministe

Le temps est une horloge virtuelle qui avance par images de 16 ms. Minuteries et animations la suivent : une exécution n’attend jamais et n’échoue jamais au hasard.

Des sélecteurs lisibles

Désignez un widget par son libellé, par son type et son libellé, par son id ou par un point. Des règles claires tranchent quand un libellé apparaît deux fois.

Des échecs clairs

FAIL line 9: … indique la ligne et ce qui a été trouvé à la place. Le script continue, et le code de sortie renseigne la CI.

Un seul langage partout

Les mêmes scripts tournent sous Windows et Linux, et pilotent aussi l’inspecteur.

Tout ce qu’une personne peut faire.

Et quelques choses qu’une personne ne peut pas faire : un script peut déposer des fichiers venus d’un autre programme, suspendre l’application, lui fournir des mesures de capteurs ou lui faire perdre le GPU, le tout sans vrai appareil.

Vérifiez ce qui compte, jusqu’au pixel.

Les assertions lisent les états, les valeurs, les textes et les rectangles dans les mêmes données que celles que voient les lecteurs d’écran et l’inspecteur. Quand les pixels comptent, un script compare un point, une zone ou toute la fenêtre à une image antérieure, octet pour octet.

  • États : exists, focused, checked, disabled, selected, open, pressed et d’autres encore.
  • Valeurs, plages, textes et rectangles en pixels indépendants du périphérique.
  • Jetons de thème, style utilisé, sons demandés et avertissements affichés.
  • --verify-dirty compare chaque rafraîchissement partiel à un rendu complet : aucun pixel oublié ne peut passer inaperçu.
expect button:"Send" disabled
type "Hi"
expect button:"Send" enabled
expect #140 value 40..60
expect text:"Saved" exists
expect #9 rect * * * 36
expect pixel 12 40 #0067C0
expect token accent_text #FFFFFF

shot before.png
theme dark
theme light
expect same before.png       # octet pour octet

Le budget par image, testé.

bench chronomètre de vraies images pendant que les choses bougent : une animation, un glissement, une série de tours de molette. Il affiche la moyenne, la médiane et la pire image et, avec une limite, échoue quand la médiane dépasse le budget. Trois essais absorbent les à-coups d’une machine de build chargée.

Le test de performance de JFNetworker déplace la vue, zoome et fait glisser de cette façon un réseau de 500 appareils et 800 câbles en 1920 × 1080.

# 300 images d’un glissement, 16,6 ms au plus chacune
bench 300 drag #50 900,500 16600

# défilement fluide
wheel 500,400 -360
bench 60 anim 16600

Chaque animation de ce site est un script.

Les GIF et les captures d’écran de ce site n’ont pas été enregistrés à la main. Un script amène chaque application dans le bon état et prend une image après chaque étape, sans fenêtre. Relancez-le après une modification, et les images se mettent à jour d’elles-mêmes.

Les voir sur la page Fonctionnalités

Chaque nouvelle application démarre avec un test qui passe.

cargo jflib new écrit tests/smoke.uis à côté de votre code. cargo jflib test compile l’application et exécute chaque script de tests/. Une première ligne #!args transmet des arguments au programme, et dump affiche l’arbre des widgets avec les ids et les positions quand vous écrivez un nouveau script.

L’inspecteur affiche le sélecteur de tout widget que vous pointez, prêt à être collé.
