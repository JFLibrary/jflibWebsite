What's coming next.

JFLib is under active development. These are the big steps ahead. There are no dates, and the order can still change.

Done Next Planned
In progress

GPU support

A GPU layer inside the library, for interfaces, 2D CAD and 3D games, with one API on every platform. The widgets keep being drawn on the CPU, so they stay pixel-identical. The GPU takes over output, layers, images and canvases.

  1. GPU layerCompute shaders, depth-tested rendering and swapchains, with Vulkan on Windows.
  2. Shader compilerWGSL to SPIR-V, inside the library.
  3. Interface on the GPUOutput with vsync, layers and canvases that pan and zoom, on Windows.
  4. More platformsVulkan on Linux and Android, WebGPU in the browser.
  5. 3D engine and CADA 3D engine core and a 2D renderer for CAD.
  6. MetalFor a native port to Apple's systems.
Planned

Native macOS

Today, JFLib apps reach macOS through the browser. The goal is a real native app with Cocoa windows and desktop integration, and Metal for the GPU layer. A native iOS version is on the list as well.

Planned

3D engine

An engine core on top of the GPU layer, grown from the test scene that already runs today.

  • Scenes, meshes and materials
  • Light and shadows
  • Visibility on the GPU, and instancing
  • glTF import
  • Later: animation, large worlds, physics and tools
1.71 msper frame for one million moving cubes at 1080p, with the GPU deciding what is visible and writing its own draw calls.
90 msfor the same scene with one draw call per object.

JFLib's GPU test scene on a GeForce RTX 2070 SUPER and a Ryzen 5 3600.

Planned

Crates and Cargo

Today a Python script calls rustc directly, which makes outside crates hard to use. The goal is to use JFLib from a normal Cargo project and to publish it as crates. The details are still open.

# today
python build_rs.py run hello --target win

# the goal
cargo run

Also on the list.
